# Response headers, and why each one is set the way it is

`vercel.json` is JSON, so it cannot hold comments, and the header block is the
one part of this repository where the *reasoning* matters more than the value.
This is that reasoning.

---

## The Content-Security-Policy

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https:;
font-src 'self' data:;
connect-src 'self' https: wss:;
media-src 'self' https: blob:;
worker-src 'self' blob:;
manifest-src 'self';
frame-src 'self' blob:;
object-src 'none';
base-uri 'self';
frame-ancestors 'none';
form-action 'self';
upgrade-insecure-requests
```

### What it is defending

Access and refresh tokens live in `localStorage` (see `shared/api/token-store`
for why: the API and the PWA are on different origins, so `httpOnly;
SameSite=None` cookies are third-party and blocked by Safari and Chrome). That
is an accepted trade-off, and its consequence is exact: **any script that
executes on this origin can read both tokens.**

The app also renders user-authored HTML into a `contentEditable` and mounts it
with `innerHTML`, which is the highest-risk pattern in the codebase. There is a
real sanitiser on both sides of the wire and it is a good one — but a sanitiser
is a single point of failure, and this policy is the second one. Without a CSP,
a bypass is a stolen session. With `script-src 'self'`, a bypass injects markup
that never runs.

### Directive by directive

- **`script-src 'self'`** — the load-bearing line. No `'unsafe-inline'`, which
  is why `public/theme-init.js` is a file rather than the inline block it used
  to be: an inline theme guard is the conventional pattern and it would have
  forced `'unsafe-inline'` on, re-enabling every injected `<script>` on the
  page. No `'unsafe-eval'` either — the production bundle has no `eval` in it,
  and if that ever changes it should be a decision, not a regression.

  `/registerSW.js`, generated by `vite-plugin-pwa`, is same-origin and covered.

- **`style-src 'self' 'unsafe-inline'`** — inline styles *are* allowed, and
  this is the one real compromise in the policy. Framer Motion animates via
  `style` attributes, and the app sets colours from data (`style={{
  backgroundColor: project.color }}`) throughout. Removing it means either
  nonces on every animated element — which is not a thing Motion can do — or
  losing the animation layer. The exposure is far smaller than the script
  equivalent: injected CSS can restyle the page, but it cannot read a token.

- **`connect-src 'self' https: wss:`** — deliberately broad. The API origin is
  a build-time variable (`VITE_API_URL`), so pinning it here would mean this
  file has to be edited in lockstep with an environment variable in a different
  dashboard, and the failure mode of getting that wrong is *every request
  blocked*. `https:` and `wss:` still forbid plaintext exfiltration and are
  narrower than the default.

- **`img-src` / `media-src` allow `https:`** — user uploads are served from
  Cloudflare R2 on a bucket-specific hostname that, again, is configured
  outside this file. `blob:` and `data:` are needed by the client-side image
  downscaler before an upload is presigned.

- **`frame-src 'self' blob:`** — the text board frames an imported PDF so it
  can be read where it sits. There was no `frame-src` before it, so framing
  fell through to `default-src 'self'` and the preview was simply blocked.
  `blob:` is the narrowest thing that unblocks it: the file is fetched *through
  the API* — which checks the project's roster on the way, something an
  unguessable storage URL cannot do — and framed from an object URL built in
  the page. Allowing the R2 hostname instead would have opened framing to a
  whole third-party host, for every page in the app, to serve one feature.

  A `blob:` frame is same-origin, so this is only safe because a blob's
  recorded type is authoritative and never sniffed: `documentApi.sourceObjectUrl`
  rebuilds the blob as the mime the API recorded at upload, so the frame gets
  the PDF viewer or nothing. It can never be talked into rendering the bytes as
  same-origin HTML.

- **`object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`,
  `form-action 'self'`** — the four that cost nothing. They close plugin
  embedding, `<base>` hijacking (which can redirect every relative URL on the
  page), clickjacking, and form posts to a third party.

- **`upgrade-insecure-requests`** — belt and braces with HSTS below.

### Verifying a change to it

The policy fails *closed*: a mistake here does not degrade the app, it breaks
it. So after any edit, load a production build (`npm run build && npm run
preview`) and check the browser console for `Refused to …` messages on:

1. first paint (theme + skin applied, no flash of the wrong palette),
2. sign-in (the API call and the socket connection),
3. a page with a user avatar and a project banner (R2 images),
4. anything animated — opening a modal is enough,
5. a project's **Text board** tab with an imported PDF open (the `blob:`
   frame).

## The other headers

| Header | Why |
|---|---|
| `Strict-Transport-Security` | A year, with subdomains. Standard, and required for the preload list if that is ever wanted. |
| `X-Content-Type-Options: nosniff` | Stops a browser deciding an uploaded file is HTML because it looks like it. |
| `X-Frame-Options: DENY` | Redundant with `frame-ancestors` for modern browsers; kept for older ones. |
| `Referrer-Policy: strict-origin-when-cross-origin` | Project ids live in URLs; this keeps them out of third-party `Referer` headers. |
| `Permissions-Policy` | Camera, microphone, geolocation and FLoC all off — the app asks for none of them. |
| `Cache-Control` on `/assets/*` | Content-hashed filenames, so a year and `immutable` is safe. |
| `Cache-Control` on `/sw.js` | The opposite: the service worker must always be revalidated, or a bad one pins itself. |

---

## What this does *not* fix

The refresh token is still reachable by script on this origin. The structural
fix is to move it to an `httpOnly` cookie on a shared parent domain, which
requires hosting the API at `api.<same-domain>` as the PWA. Until that happens,
this policy is the mitigation, not the cure — and it is worth re-reading
`token-store.ts` before assuming otherwise.
